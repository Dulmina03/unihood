# Public POI candidate engine — UNI-023

Specification §6.1–6.3, §8.5 and exact §10 UNI-023. Depends on UNI-020/021/022 and all [five accepted ADRs](../decisions/README.md). Internal `PoiMatcherService` is registered for later guarded integration, not exposed through a new REST route. UNI-024 owns warning API/UI, UNI-025 final transactional/idempotent proposal checks and pending sources, UNI-026 guarded contribution flow. No production write, registration/provider policy, canonical merge or UI feature is introduced here.

## Name normalization and retained identity

`normalizePoiName` in shared contracts uses NFKC, Unicode lowercase, punctuation/symbol boundaries and collapsed spaces. Letters/numbers/combining marks and ZWJ/ZWNJ are retained, preserving Sinhala/Tamil vowels/shaping. No accent removal, phonetic probability or invented transliteration; approved multilingual aliases supply actual alternative names. Original display names and aliases are retained unchanged. The key is not a unique real-world identity: different businesses may normalize identically.

Inputs are strict public POI proposals (kind POI, category/name/public point), optional exact provider+external-ID or public building UUID, 1–200m radius (default illustrative 50m), 1–20 results (default ten). Names are limited to 200 raw and normalized characters; control/bidi-only/punctuation-only names and unknown residential/identity/media fields are rejected. NFKC expansion cannot create an unbounded scoring key. Provider/external IDs are opaque exact identities and are not name-normalized.

No backfill rewrites existing records or changes UNI-021 seeds. Bounded candidate raw names/aliases are normalized on each read, including legacy matching keys. Future write/import workflows should reuse the versioned helper; silently replacing original names or treating normalized_name uniqueness as identity is prohibited.

## Candidate retrieval and deterministic scoring

Only active, unmerged POIs with explicit public-location rows enter retrieval. Synthetic rows use the existing guarded local/test environment policy; deployed/missing/unknown environments exclude them. No private boarding/building geometry, unpublished/pending proposal geometry or hidden-location proximity is read. Known public POI building membership is supporting context only; deployed synthetic/archived building references do not create a shared-building signal.

Candidate sources are a UNION of public geography-radius points, eligible exact source IDs (even after provider geometry drift), and eligible shared-public-building members. Geography ST_DWithin uses metres, including date-line/polar behavior; it is not a walking route/radius estimate. New migration 004 provides the matching geography-expression GiST index; existing geometry bbox/index and trigram indexes remain untouched.

Retrieval returns at most 201 rows, prioritizing exact source, shared building, then UUID. Score at most 200 rows and 20 aliases each. An extra row/alias sets `incomplete`; no caller may treat an incomplete/empty result as clearance to create. Very dense scopes can omit a better match after the cap; this is explicitly signaled rather than falsely claiming exhaustive nearest/best results. `hasMore` separately indicates more scored candidates than the requested result count.

Normalize this bounded snapshot once, then ask PostgreSQL `similarity` for the maximum name/alias score per ID in a parameterized JSON recordset. This avoids an unbounded text scan, legacy normalization drift and mutable pooled similarity-threshold GUCs. Existing trigram indexes are not falsely claimed to accelerate this small post-retrieval batch. Spatial/source/building queries use their relevant indexes; the repository's existing statement/query timeouts remain. New fixtures prove the geography expression index is usable, not production p95 performance.

Illustrative version `public-poi-v1`: retain similarity >=0.25 or exact-source/shared-building evidence. Ranking score = round(70×name similarity +15 category agreement +10 within radius +5 shared building); exact normalized canonical/alias text sets name similarity to 1, and exact provider ID starts at score 100. Category conflict caps at 49; shared building without exact provider identity caps at 79 and requires conflict review. Otherwise score >=80 or exact source is STRONG_CANDIDATE; lower evidence is POSSIBLE_CANDIDATE. Conflicts are REVIEW_REQUIRED. Ties use UUID. All results, including empty ones, have `requiresReview:true` and `scope:PUBLIC_POI_ONLY`.

Scores and bands are tunable synthetic heuristics, **not probabilities or verified identity**. Equal text, a shared building, a provider key or proximity never authorizes a merge, privilege transfer or publication. Unit/operator evidence is not modeled yet; co-located identity ambiguity stays reviewable. Later final submission must recheck under its transaction; this engine does not reserve identities, prevent concurrent writes, rate-limit an absent API or expose a create/merge command.

## Privacy and unfinished scenario coverage

Output has public canonical ID/name/category, ordinal score, bounded boolean/similarity signals and review flags. No coordinates, precise distances, aliases, building IDs, private fingerprints, contacts, images or provider IDs are returned. Runtime schemas validate SQL projections and result shapes. Unknown/malformed input fails before query; SQL values are bound. Both engine queries run successfully in actual read-only transactions. Exact private boarding source IDs cannot bypass the POI/public-location predicate. No authorization is granted by arbitrary identity headers or these internal schemas, which are deliberately absent from public OpenAPI.

The isolated JSON dataset is [explicitly fictional](../../infra/db/fixtures/poi-matching.synthetic.json), not a development seed/import. The dataset and owning harness cover a pharmacy typo with PostGIS-generated 12m drift; same-name different towns; adjacent co-located businesses; shared public restaurant/category conflict; Sinhala/Tamil aliases; full-width legacy names; moved provider geometry; archived/pending/merged/unlisted and boarding exclusions; date-line/polar searches; 49/51m boundaries; score/cap ordering; concurrent independent read-only calls; more than 200 points/20 aliases; and read-after-explicit-fixture restoration. Snapshot checks prove no matcher mutation. The fixture restore is not an implemented merge/reversal workflow.

The complete §6.3 Phase 2/whole-product matrix is **not finished by UNI-023**. Two private boarding operators, student recommendation reconciliation, hidden-ad owner claims, property-scoped contact evidence, image recompression/shared-stock-photo matching, pending submission reservations and actual concurrent submit idempotency require later schemas/consent/actor workflows. This engine rejects private/media input or excludes nonpublic rows; it does not pretend to match those scenarios. The public restaurant/private boarding exclusion fixture proves separation, not an implemented upstairs boarding association. Pending proposal checks must be added before UNI-025/026 submission can be considered complete. No real-world matching accuracy or human calibration is claimed.

## Operations and references

Apply the new index with normal `pnpm db:migrate` after backing up as appropriate; do not reset/delete a volume. This issue's verification runs migrations only on disposable Docker storage. Migration 004 creates an index without IF NOT EXISTS, refusing to silently adopt a conflicting object. Rollback removes that index only, even with populated POIs; original 003 still refuses populated-table deletion. It changes no stored names, data, consent, ownership or extensions. Regular transactional index creation can briefly block writes; production migration scheduling/performance is a later reviewed deployment concern. No concurrent-DDL workaround or shared migration history edit is introduced.

Technical references: [PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html) (geography metres/index support), [PostgreSQL pg_trgm](https://www.postgresql.org/docs/17/pgtrgm.html) (similarity vs threshold operators). Runtime behavior is independently checked on the pinned PostGIS/PostgreSQL 17 image.
