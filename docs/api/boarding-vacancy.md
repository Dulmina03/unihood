# Synthetic unit vacancy confirmations — UNI-036

[Specification](../../UniHood_MASTER_PROJECT_SPECIFICATION.md#phase-3--boardings-advertisements-privacy-and-vacancy-m3m1m2) §3.5/§6.4, [property authority ADR](../decisions/0003-property-specific-owner-authority.md), [inventory/fees](boarding-inventory.md), [OpenAPI](openapi.json), [actual verification](../verification/UNI-036/README.md).

Availability is an explicit owner assertion per unit, independent of capacity, price or map visibility. Only the existing issued synthetic owner-a adapter can confirm the preinstalled fictional property A. Management AND CONFIRM_VACANCY are required for the exact property; a price-only manager, contributor, arbitrary identity header or unrelated property grants no authority. Staging/production writes stay denied. No real vacancy, ownership proof, booking offer or production authorization is introduced.

Protected `POST /api/v1/boardings/:id/vacancy-confirmations` accepts unitId, expectedUnitRevision, expectedVacancyRevision, status, availableBeds and reason only. AVAILABLE requires an integer count greater than zero and no greater than the current declared capacity. FULL confirms zero; UNKNOWN confirms no count. INITIAL is required for the first revision; subsequent reasons are RECONFIRMATION, STATUS_CHANGE or CORRECTION. Actor, confirmation time and expiry are server-controlled. Client clocks, TTL overrides, identity and location fields are rejected.

The transaction locks and rereads the property and exact unit, then appends history and advances its vacancy revision atomically. A stale unit or confirmation revision returns 409. Editing a unit capacity/template changes its unit revision and invalidates the previous current confirmation without deleting history. A fee change never reconfirms vacancy. Historical author references are stored internally but absent from every public/history wire payload.

`VACANCY_TTL_DAYS` is a bounded integer 1–365. Missing configuration uses the specification's provisional 14-day example, not a finalized real-world policy; `.env.example` documents that value. Invalid configured values fail confirmation closed with a generic 503. Each confirmation stores its expiry, so later policy changes affect new confirmations without rewriting historical facts. Final operational TTL still needs real owner interviews/release review.

Public room facts continue through `GET /api/v1/boardings/:id/units` and its no-store Next adapter. Only the latest confirmation for the current unit revision can qualify. Missing/invalidated/future-dated confirmations are UNKNOWN with no current count. Expired AVAILABLE or FULL assertions become UNKNOWN with no available-bed count, retaining minimal last-confirmed/expiry/source context. Explicit UNKNOWN also retains its confirmation dates. Server database time is authoritative; client rendering additionally suppresses an expired/future assertion and schedules expiry on an already open page, including TTLs beyond the browser timeout maximum. Browser focus/page-show revalidates public facts. This is not a push-based freshness SLA or booking guarantee.

Legacy advertisement and map summaries do not aggregate unit availability; their room-facts links lead to current unit confirmations. Community recommendations never acquire official status from a raw count. No geography is read to authorize or display availability, so HIDDEN/AREA_ONLY owners are not forced into public map consent. No distance, route or location is inferred or stored/shared by the controls.

Owner inventory includes the latest 20 confirmation revisions per unit. Protected `GET /api/v1/owner/boardings/:boardingId/units/:unitId/vacancy-confirmations?page=2&pageSize=20` makes older history reachable, in revision order. All pagination is bounded and strict. No deletion/update-history endpoint exists; this is append-only through the API, not an immutability claim against database administrators.

Migration 011 adds a separate confirmation table and default-zero high-water revision; all existing migrations/rows remain intact. Constraints cover property-unit identity, status/count/capacity snapshots and finite ordered dates. Populated or changed-metadata rollback refuses and preserves data; external dependencies refuse atomically with RESTRICT. No extension change or CASCADE.

## Local synthetic demonstration

Use the existing [inventory setup](boarding-inventory.md#local-synthetic-demonstration); preserve existing data and review/add the migration using `pnpm db:migrate`. Do not reseed/reset an edited fixture to silence a conflict. Start the explicit loopback owner-a adapter and web. In `/owner`, open Availability & expiry, load current inventory, deliberately select a fictional unit and confirm Available with a count, Full or Unknown. A room must already exist; no unit or confirmation is invented for empty inventory. The server returns stored status/expiry/history after each save. Ambiguous errors clear editable state and require reload before a deliberate retry.

Open Public room facts to see the current synthetic assertion, explicit count, last-confirmed/expiry dates in Asia/Colombo, or UNKNOWN. Changing capacity requires a fresh confirmation. Browser screenshots/mock responses prove UI behavior only; real API/database evidence is separate in verification. Production owner writes and final registration remain deferred.
