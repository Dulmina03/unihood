# Held public POI corrections and own contribution history — UNI-042

Specification §3.6, §7.3–7.4, §10 UNI-042; ADRs 0001–0005 remain intact. Only an issued loopback local/test contributor capability can use these endpoints. Guests, staging/production/unknown modes, arbitrary identity headers, cross-site and forwarded requests cannot select an actor or gain authority. No final registration, public publication, boarding correction, owner fact change or support dashboard is implemented.

`POST /api/v1/contributions/correction` accepts strict `{key,placeId,change,observedOn,evidenceNote,publicBusinessConfirmed:true,syntheticAcknowledged:true}`. The target must currently be an active, unmerged SYNTHETIC public POI with a public location. A boarding, unlisted/archived/merged or unknown target has the same unavailable result. The current canonical record is locked/read inside the transaction; the application never updates it.

Changes are NAME (Synthetic-prefixed name), CATEGORY (existing public-service category), CLOSURE (temporary/permanent observation), MOVED (valid fictional public-service entrance), or DETAILS (bounded permitted context). A moved point is retained only as a held private proposal; it never changes a canonical pin or authorizes residential geometry. Observation dates are valid calendar dates, no later than the current UTC date. Textual evidence is 15–400 characters with control/bidi restrictions; no file, evidence URL field, private contact or ownership input is offered. This is fictional evidence context, not verified testimony or confidential-report handling (UNI-044).

Migration 015 stores an actor-scoped immutable-intent held record with a canonical FK, action, hash, private payload, observed date, review state and submission time. All corrections are held. Closure/movement always need evidence; conservative existing text signals can also require evidence, and their absence never certifies safety. Actor/key/payload replay is idempotent; changed payload returns 409 without overwriting history. A different actor has a separate receipt. Failure rolls back atomically. Populated rollback refuses and RESTRICT protects dependencies; earlier migrations remain immutable.

Success 200/no-store contains only own contribution ID, currently eligible public place ID or null, HELD_CORRECTION, PENDING/NEEDS_EVIDENCE, SYNTHETIC and `published:false`. On same-key replay after public source withdrawal, retain the original held record and suppress its source ID. Never expose private source details or silently substitute another canonical target.

`GET /api/v1/contributions` is protected even though it is a GET. It returns only the requesting actor's held POI corrections, stored POI proposals and boarding recommendations. Query: optional `kind`, `state`, `page` 1–10000 and `pageSize` 1–100. Stable newest/date/kind/UUID ordering and one-row overfetch supply `hasNextPage`; no other-actor total is exposed. URL/header-selected actors and unknown query fields are rejected.

The strict history item includes ID, kind, current held state, submission timestamp, SYNTHETIC, optional currently eligible public POI target and correction action. No draft names/text, proposed coordinates, residential target links, contacts, source notes, risk flags, pending match evidence, payload hashes or actor IDs are projected. Legacy submissions have an actual created-at timestamp; the UI's submission history identifies that recorded event, not a fabricated moderation transition. Unsent drafts, preflight checks and canonical redirects without a stored submission are not history records. Published/rejected decisions and notifications remain later governance work, not simulated successes.

UI-26 `/contributions` supports held-state/type filters, pagination, refresh/retry, unavailable/empty/loading states and expandable submission records. `/contribute/correction?place=<canonical-public-UUID>` starts from the existing public detail's correction link; malformed/extra query fields do not select a target. The form supports all five actions, source inspection/reload, review of actual proposed changes, explicit synthetic/public-service acknowledgement, unchanged-request retry and held receipt. Drafts remain in memory and are excluded from local/session storage and share URLs. Both pages use generic noindex metadata; all API calls use no-store/omit credentials. Clearing local inputs cannot retract a server-received request.

Local demonstration: use the existing synthetic database and migration/seed instructions. Explicitly run the loopback local API with `APP_ENV=local`, development Node mode, `ENABLE_SYNTHETIC_ACTORS=true`, `SYNTHETIC_ACTOR=contributor`, matching `WEB_PORT` and `API_HOST=127.0.0.1`. Start `pnpm dev`; browse a seeded public POI, expand “Information looks wrong?”, and choose its correction link. Use fictional context only. Review and submit, then open “Your contributions”. Normal guest services stay read-only; no public server should enable this simulator.
