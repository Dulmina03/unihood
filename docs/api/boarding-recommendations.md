# Boarding recommendation intake and privacy-safe choices — UNI-040/041

`POST /api/v1/contributions/boarding` is the specification §7.4 route, protected through the existing issued contributor capability. Only explicit loopback local/test actors and synthetic data are accepted. Staging/production/unknown environments, guests, forged identity headers and cross-site/forwarded requests are denied. This capability grants no property manager permission.

The shared strict input has `key` (UUID) and `draft`: a Synthetic-prefixed title, bounded description, nullable closed synthetic broad locality, unique allowlisted facilities, `privacyAcknowledged: true` and `mediaGuidanceAcknowledged: true`. Unknown fields are rejected, including coordinates/pins, official prices, confirmed vacancy, owner flags, contacts, media URLs, actor IDs and publication state.

Success 200/no-store returns only contribution ID, HELD_RECOMMENDATION outcome, PENDING/NEEDS_EVIDENCE review state, COMMUNITY_RECOMMENDATION publisher, SYNTHETIC provenance and `published: false`. It is a private receipt, not a public listing/share URL. Same actor/key/canonicalized draft replays; a changed draft returns 409. Facility order does not change intent. A different actor cannot retrieve another actor's intake through the same key. Requests share the existing bounded local contribution budget and a three-active-request transport cap.

Migration 013 stores private held intake with no geometry, official fact or canonical publication columns. All drafts are held, regardless of text signals. Contact/address/link signals request evidence; their absence never proves content safe. No canonical boarding/listing, owner membership or public media is created. No routine admin UI, enrollment proof, final authentication or real publication is implied. UNI-041 implements privacy-safe duplicate association and UNI-045 later risk/publication rules.

`/contribute` and `/contribute/boarding` reuse the design system. The latter uses public `/boardings` title search only; it is not duplicate clearance or a private lookup. No media upload is offered: community permissions do not authorize owner private quarantine. Drafts remain in memory, clear on reload and are excluded from browser storage/share URLs. A request already received by the server is not cancelled by clearing local inputs.

Local demonstration: use the existing synthetic `.env.example` setup, run migrations with the normal safe runner, then explicitly configure the loopback API as `APP_ENV=local`, `ENABLE_SYNTHETIC_ACTORS=true`, `SYNTHETIC_ACTOR=contributor`, `API_HOST=127.0.0.1`, with the development Node environment. Start `pnpm dev`; open `/contribute`, choose Recommend Boarding, use the fictional example, acknowledge privacy/media guidance, review, check public matches, explicitly select an existing advertisement or explain a distinct suggestion, then submit for review. This actor cannot edit official fees/vacancies/map consent. Do not enable protected write simulation on a public server or enter real private information. Final account/owner proof remains Phase 7.

See [actual verification and limitations](../verification/UNI-040/README.md) and [Phase 4 progress](../progress/PHASE-04.md). No remote result is implied by this document.

## UNI-041 public-text duplicate choices

Protected `POST /api/v1/contributions/boarding/duplicates` takes only `{title, locality}`. It reads current curated synthetic HIDDEN/AREA_ONLY advertisement text, never raw listing descriptions, canonical private names, geometry, contacts, building relationships, media fingerprints or pending drafts. HIDDEN locality is unknown, never inferred or used to exclude a possible public match. AREA_ONLY locality must remain consented and match the current property. PUBLIC_MAP records are outside this private-advertisement flow.

The Unicode-normalized name signal uses NFKC/case normalization and trigram overlap, with a provisional 35/100 candidate threshold. It is not a probability, calibrated accuracy guarantee or transliteration engine. Only the first 100 deterministically ordered eligible public records are scanned; at most five matches are returned. `incomplete`/`hasMore` disclose bounded public search limits. No result ever clears a draft as new.

`POST /api/v1/contributions/boarding/resolve` adds explicit `resolution: {kind: "EXISTING", boardingId}` or `{kind: "DISTINCT", reason}` to the original intake. All submissions stay private and held. Existing selections are checked again inside the intake transaction and linked to the same canonical ID in private migration 014; no canonical record, owner authority, public advertisement or pin is created. Current property locks serialize against owner visibility changes. Same-key changed draft or selection returns 409, never rewrites history. A replay whose source is no longer public returns REVIEW_REQUIRED/null without removing private association history. The response grants no owner permissions.

Distinct choices require a bounded reason and remain NEEDS_EVIDENCE. A bounded first-100 private pending-title scan can retain a possible internal relationship at provisional score 80; another contributor's pending ID, content, count and match result never leave the server. The outward response is always REVIEW_REQUIRED/null. Shared buildings, similar names and shared contacts do not prove identity. No destructive merge or public identity creation occurs. Authorized contact/image fingerprints and real-world matching calibration remain unavailable and are not simulated as proven evidence. Private resolution associations have restrictive FKs, PUBLIC ACL revoked, immutable intent hashes and populated-data rollback protection.

The UI requires an explicit choice, supports retry without silent identity changes, discards stale responses after edits, and excludes drafts/receipts from storage, share URLs, SEO and public caches. Existing advertisement links use the canonical boarding ID. Clearing the form cannot retract a server-received request. Both new endpoints share the existing rate budget and use no-store; the original intake endpoint also retains its existing three-active-request cap. No new transport-cap claim is made for these endpoints. Final identity, owner proof, publication and appeals remain later roadmap work.
